# 测试 → Obsidian → 可选视频 → 飞书报告

## 用户约定：先看链路，再按条件执行

首次进入新任务展示以下导航，并说明本次从哪一步接入。阶段不适用则明确跳过；不要为了补齐链路启动额外评测。后续单纯进度追问不重复整张表。

> 本次链路：配置 → 测试/监督 → OB记录 → 视频/GIF（可选）→ 图表报告 → 飞书子页面 → 验收。以下是已知条件，你可以直接补充任一环节；已明确的部分按原要求继续。

| 环节 | 展示已知条件；允许用户补充 | 验收输出 |
|---|---|---|
| 测试配置 | 模型/bundle、场景、次数、H、动作上限、种子、成功判据、初态与单变量约束 | 冻结plan/contract及模型哈希 |
| 执行/监督 | 新建/续跑/只读、并发占用、预算、超时、停止点 | 实际PID、日志增长、终态覆盖；不凭旧running判定 |
| OB记录 | 确切vault/子目录、自动或手工报告、刷新频率、完成/中断归档 | 本地与vault首份及终态一致；索引可达 |
| 视频/GIF（可选） | 不需要/复用已有/新增采集；成功/失败、配额、视角、选择规则、来源、发布目的地 | manifest、样本身份、视角配对、哈希、解码及预览 |
| 图表报告 | 最新/全部轮次、截止快照、面向领导或技术交接、只图表或允许分析、历史比较范围 | 冻结数据表、图、草稿和证据清单 |
| 飞书 | 新子页/更新已有页、确切父节点或目标URL、标题、包含哪些素材、何时发布 | 文档ID、Wiki节点ID、revision和父节点关系 |
| 验收 | 覆盖/百分比/表格/素材/目录、剩余缺口 | 回读检查及最终可打开链接 |

只问会阻塞下一步的缺失条件。可用异步问题收集偏好，同时继续独立准备；没有回答不等于授权。用户已给定整条链路、目标和条件时，无需逐阶段重复确认。用户改变模型、成功判据或执行协议时新建批次；只改报告风格不重启测试。

默认沿用已确认的横向成功率图＋表格风格，保留成功数/有效分母和阶段状态；用户明确要求极简时不堆叠长篇解释。必要边界写成紧邻图表的一行或一行表格。

## 已具备什么，尚未自动化什么

截至2026-09-18的核对，不是实时进程状态承诺：

| 部分 | 证据/成熟度 |

实现核对入口：测评仓库 `tools/a2d_eval_loop/docs/AUTO_REPORT.md`、README及实际源代码。本次查看的分支为 `feat/a2d-eval-loop-v0`；后续必须重查版本。observer对多个mode的展示可能合计，使用前核对支持边界，不能跨执行方式静默混算。

完整自动化的代码继续归属测评仓库，skill只维护执行条件和验收。若用户另行要求实现，应整合现有能力，不将本次临时绘图脚本照搬成第二个评测/报告后端。

## 从Obsidian冻结报告输入

- 先读索引、最新人工分析与自动报告；时间更晚的记录优先，但必须批次、场景和指标一致。保留截止时刻，不把阶段快照当实时全量结果。
- 机器可读的原始ledger及contract是统计依据；仅有笔记时标注“依据归档笔记”，不声称本轮重算过逐物理步信号。
- 比较使用成功/有效，同时保留尝试、无效、策略拒绝；区分曾持续成功和最终保持。模型名、权重、场景、mode、判据变化不能合成一个全局排名。
- 全轮次整理对源表做逐行覆盖核对，重复交接、冻结快照与后续追加不是新增独立实验。诊断参考命中不标成抓取成功。
- 未完成、未记录、基础设施无效不改写成0%失败。未匹配初态或小样本只报观察差异。

## 视频资料的来源与证据

- 先确认远端是SSH运行目录还是GitHub展示分支；不能从成功画廊分支推断不存在失败画廊。精确来源未知才询问。
- GitHub素材固定commit；读取manifest及SHA256SUMS，检查同模型/场景/episode双视角配对、唯一样本数、GIF全帧解码、循环和播放时长。
- 实际文件可能与manifest的编码元信息不同。本案例manifest写101帧而发布GIF解码为81帧；如实记录差异，不把推测当编码原因，不改原媒体来凑元信息。
- 成功或失败定向采集与正式测试是独立批次。相同模型/参数不代表GIF来自当前百次测试；标签中说明来源，不从展示配额计算模型优劣。
- 不从旧seed/action日志捏造原始视频。需要新增采集时先处理其测试参数、资源占用和授权；缺GIF时继续准备数据报告，说明缺口，不用无关图代替。

## 飞书生成与目录验收

1. 读取当前CLI内嵌lark-doc/lark-wiki工作流；新文档显式传入已解析父节点，例如 `docs +create --parent-token <parent_wiki_token>`。默认位置遗漏会创建不在Wiki目录树的独立文档。
2. 沿用user身份。目标名称可沿用用户约定的“A2D/a2d il测试记录”，但token和所有者必须从当前链接/本机配置解析并核对，不把内部ID写进可迁移skill。
3. 新建子页需用户明确创建请求。修改已有页前核对标题/类型/所有者及只读有效权限API；非本人所有或无法确认所有者时，展示具体目标和改动后单独确认。不以试写探测权限，不切换bot绕过失败。
4. 本轮用户对确切报告和目的地的发布请求可以覆盖其中已说明的图表/GIF，无需重复确认每张图。配置中的父节点只是默认目的地，不是未来每轮发布授权。
5. 登录凭据过期与权限缺失分开处理；先检查原user登录及已有scopes，恢复登录后复用已有权限。不要把过期解释为所有权限均需重授，不为排障直接申请all权限。
6. 先完成可复核草稿、中文字体与图像检查、XML格式检查，再创建/局部更新。创建响应不明确时先查询已建资源，不盲目再次创建。
7. 写后重新fetch，核对表格单元格、成功分母、图片/GIF数量与类型；另查Wiki节点，确认 `parent_node_token` 等于指定父节点。正文写入成功不等于目录交付成功。
8. 返回可打开的Wiki链接和父子路径。保留本地证据manifest；不上传凭据、OAuth临时链接或原始会话。

## 后续自动化需要的最小状态（设计约定，尚非已实现接口）

为每批次记录：batch_id、协议/源记录哈希、快照时间、各阶段条件与状态、observer身份、OB输出路径、媒体manifest/commit、文档ID与父节点、最后已发布快照哈希、回读验收结果。

按冻结快照哈希判断是否需要更新，重复执行不得重复建页；状态建议 planned/running/complete/partial/blocked/skipped。素材缺失、登录失败或发布失败应只阻塞相应环节，不停止正常评测；发布失败不触发重新采集。认证和目标资源权限仍按当次用户授权检查，不能只依赖持久状态中的布尔值。

真正落地还需在仓库实现并验证：统一命令入口、媒体适配器、图表模板、飞书幂等创建/更新、完成/中断触发与恢复机制。开发顺序优先“冻结快照→本地草稿→显式请求发布”，稳定后再做范围明确的自动触发。
