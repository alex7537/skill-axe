# 添加登录公钥后，旧客户端报告主机身份变化

## 已有案例与证据边界（2026-09-16）

- 用户报告：为了让另一台客户端登录 TI-ONE 开发机，平台操作流程要求停止开发机、编辑登录公钥、再启动；之后原客户端在相同 SSH 地址遇到 host key changed。
- 已观察：Linux 客户端报主机密钥冲突；随后从 Mac 进行只读扫描，端点可达，ED25519 指纹与该报错一致，且当前返回的三种主机密钥均与 Mac 已保存的同算法记录不同。
- 能得出的结论：该端点当前展示的身份与历史记录不同；用户报告变化发生在上述管理流程之后。新增客户端获准登录与旧客户端拒绝服务器身份可以同时发生。
- 未证实：本轮未进行受控的操作前后对比，未检查平台生命周期日志、实际 SSH 服务容器、启动脚本或主机密钥挂载。因此不能断言是容器重建、启动脚本生成密钥还是转发目标替换，也不能推广成“TI-ONE 每次停启都会换密钥”。
- 未完成修复验收：本次没有修改 known_hosts，也没有验证远端登录成功。用户报告的配对成功与工具实测应分开描述。

## 解释时必须保留的区别

1. “添加公钥”可能指平台的停机编辑工作流，不一定是运行中追加 `authorized_keys`。先确认操作路径，避免反复用“普通改配置不会换密钥”否定用户观察。
2. SSH 先校验服务器身份，再验证用户登录权限。首次主机密钥被接受并成功写入后，即使随后公钥登录失败，known_hosts 记录也可以保留；并非每次失败连接都会自动保存记录。
3. known_hosts 在客户端记住服务器公钥；authorized_keys 在服务端授权用户公钥；服务器主机私钥通常位于 `/etc/ssh/ssh_host_*_key`。客户端登录私钥不应上传开发机。
4. 公网端点返回公开主机密钥是正常握手行为，不等于未授权登录。host key changed 证明身份不一致，本身不能证明入侵或证明安全。
5. 本地记录通常不会无故变化；常见冲突是客户端仍保存旧身份，而相同端点开始返回新身份。逐算法比较，不能把 ECDSA 与 ED25519 的不同指纹直接当作同一密钥变化的证据。

## 如何查清平台流程

优先读取现有证据，不为诊断主动停启用户开发机。若用户已授权下一次管理操作，可采集操作前后的对照：

- 平台当前 SSHConfig 的 host/port、实例身份及平台可提供的生命周期记录。
- 通过可信控制台进入实际终止 SSH 连接的服务环境，确认 sshd 使用的 HostKey 路径，记录公钥 SHA256 指纹。默认路径示例：

  ```bash
  ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
  ```

- 比较主机密钥文件是否位于实例专属持久存储、容器或服务实例是否替换、启动脚本是否删除或重建 host keys、转发目标是否变化。仅文件时间变化不能单独证明重建根因。
- 将可信控制台读取的指纹与客户端看到的指纹核对。若控制台环境与对外 SSH 服务不是同一环境，先追踪实际 SSH 终止位置。

定位到哪一层就报告哪一层，不把某种合理机制写成已验证根因。

## 处理与长期改进

- 当前恢复：按主技能的身份核验与授权要求，仅更新实际失败客户端上对应端点的旧记录，再验证主机身份和用户认证分别成功。删除记录不是身份核验。
- 运行中添加公钥：只有确认平台支持、修改能持久化且用户已授权时才采用；不能假定手动改 authorized_keys 不会被平台覆盖。
- 同一逻辑实例跨重建：平台可将其专属主机密钥安全持久化；不要把同一主机私钥打进通用镜像供不同实例共用。
- 独立的新实例：使用明确的独立连接身份；规模化临时实例可由平台采用 SSH 主机证书及受信任 CA。二者属于平台设计选项，不是已验证存在的功能。
- 不把自动删除 known_hosts、永久关闭 StrictHostKeyChecking 当成根治方案。
